# Attribution and provenance

This file lists every file in this repository that was **not written as part of this
project**, plus the third-party code the build pulls in. For each binary, it says where
it came from and how to recreate it.

Everything here was checked on 2026-11-04 by hashing the files and comparing them
against their upstream sources. "Verified identical" means a byte-for-byte match
(same SHA-256). Anything not verified that way is labeled as such.

### `tls/prebuilt/tls.wasm`

Built by this project. It is the in-browser TLS server that lets the guest make HTTPS
requests (see `tls/main.go`). Besides the project's own code, it contains the Go
runtime and standard library (BSD-3-Clause, `vendor/go/LICENSE`). There are no other
Go dependencies: `tls/go.mod` has no `require` lines.

| | |
|---|---|
| Source | `tls/main.go`, `tls/go.mod` |
| Toolchain | Go `go1.24.7` (embedded in the binary) |
| SHA-256 | `3f8fe0a257a21216d37b9bef44e9da93849bceba8fed1d26748df037a9c6e527` |
| Size | 7,587,330 bytes |

**Recreate**. This command reproduces the committed file **byte for byte** (verified):

```sh
cd tls
GOTOOLCHAIN=go1.24.7 GOOS=js GOARCH=wasm \
  go build -buildvcs=false -trimpath -ldflags="-s -w" -o ../build/tls/tls.wasm .
sha256sum ../build/tls/tls.wasm   # 3f8fe0a2…a6e527
```

`npm run tls` (`tls/build.sh`) builds a functionally identical file with a **different
hash**. It uses whatever Go version is installed, and it omits `-buildvcs=false`, so
Go stamps git metadata into the binary when you build inside a checkout. Use the
command above when the bytes matter.

`vendor/go/wasm_exec.mjs` must come from the same Go version as `tls.wasm`. If you
rebuild with a different Go version, replace that file too (see
[Vendored source code](#vendored-source-code)).

**Recreate** with `make flex bison bc lz4` and a gcc for x86 (native on an x86-64 machine; on ARM, `gcc-i686-linux-gnu`, which the script picks up automatically):

```sh
npm run kernel          # clones v6.18 into build/linux-src, writes build/kernel/bzImage
npm run build           # build/kernel/bzImage takes priority over guest/prebuilt/bzImage
```

A rebuild is **functionally equivalent but not byte-identical**. The kernel embeds the
build time, user, host and compiler version. Setting `KBUILD_BUILD_TIMESTAMP`,
`KBUILD_BUILD_USER=root` and `KBUILD_BUILD_HOST=vm` and using the same Ubuntu 24.04
toolchain gets close; an exact match has not been verified.

On a non-x86 machine (an ARM Mac, an aarch64 dev container) `build-kernel.sh`
cross-compiles with `i686-linux-gnu-gcc` / `x86_64-linux-gnu-gcc`, or whatever
`CROSS_COMPILE` names.

**Corresponding source** (GPL): the `v6.18` tag above plus `guest/kernel.config`,
which is in this repository. The kernel source is unmodified.

### `guest/prebuilt/guest/` (`fs.json` and `rootfs/*.bin.zst`)

The VM's root filesystem, in v86's 9p image format (version 3):

- **`fs.json`** is the directory tree. Each entry is
  `[name, size, mtime, mode, uid, gid, target]`. For a regular file, `target` is the
  name of the blob holding its contents. The tree describes 7,066,878 bytes of files.
- **`rootfs/<hash>.bin.zst`** (85 files) holds the contents. Each name is the **first
  10 hex digits of the SHA-256 of the uncompressed content**, and each file is
  zstd-compressed. Identical files share one blob. Every blob was checked: its name
  matches the hash of its decompressed content.

**Where it came from.** It was produced by `guest/build-rootfs.sh` from
`guest/Dockerfile`, built **with no extra packages** (`PACKAGES=""`) on top of
`i386/alpine:3.22`, which resolved to Alpine **3.22.7**. The README notes this
prebuilt image was made in an environment without access to Alpine's package mirror,
which is why it lacks the Dockerfile's default packages (git, node, python, …).
Evidence:

- The image's package database (`/lib/apk/db/installed`) lists exactly the 16 packages
  of the stock Alpine 3.22.7 base image (table below), and nothing else.
- 71 of the 72 package-owned blobs are byte-identical to the files in Docker Hub's
  `i386/alpine:3.22.7`, image digest
  `sha256:01a8ebe5b756712f5e2a0e61cae94ddc036df435c21421735fd7e944e2186afd`
  (created 2026-10-21). The one exception is the damaged file described below.
- The project files baked into the image (`/sbin/vm-init`, `/sbin/vm-agent`,
  `/root/project/*`) are byte-identical to `guest/vm-init`, `guest/vm-agent` and
  `guest/welcome/*` in this repository.

**Known defect.** `/usr/share/udhcpc/default.script` (blob `f2f2946b66.bin.zst`) is
**damaged**. It has the right size (3,811 bytes) but scrambled content that ends
mid-line. The damage happened before the blob was created, since the blob's name
matches the hash of the damaged content. It has no effect today: this file is
busybox's DHCP client hook, and `guest/vm-init` configures the network statically and
never runs `udhcpc`. Rebuilding the image fixes it.

**Recreate** on an **x86-64** machine with Docker, Python 3 and the `zstandard` module:

```sh
BASE=i386/alpine:3.22.7 PACKAGES="" npm run guest   # writes build/guest/
npm run build                                        # build/guest takes priority over guest/prebuilt/guest
```

Expect the same blob names (except the damaged file, which comes out correct), but a
different `fs.json`: it records file modification times, which change with every
build. Pin the base image by digest (`BASE=i386/alpine@sha256:01a8ebe5…`) to guard
against the `3.22.7` tag being republished.

`npm run guest` does not work on ARM hosts. `docker build` has to execute x86 programs
for the Dockerfile's `RUN` lines, which fails with `exec format error` unless x86
emulation (binfmt/QEMU) is installed.

### Playground images (`build/playgrounds/`, not in the repository)

Generated by `npm run playgrounds` (locally, and in CI before each deploy) and
shipped in `dist/`. Each is built from:

- Alpine Linux's minirootfs for the release in its manifest
  (`playgrounds/<id>/playground.json`, currently 3.23), downloaded from
  `dl-cdn.alpinelinux.org` and checked against the release's published SHA-256;
- the Alpine packages its manifest lists, and their dependencies, installed by
  Alpine's `apk-tools-static` (exact versions are recorded in the built
  `manifest.json`; licenses per package, as for the default image);
- this project's `guest/vm-init`, `guest/vm-agent`, `guest/overlay/` and the
  playground's `template/`;
- for playgrounds with `"npm": true` (`svelte-vite`, `sveltekit`), the npm
  packages in the template's `package-lock.json` (pinned by version and
  checksum), installed from registry.npmjs.org into `/root/project/node_modules`.
  These include Svelte, SvelteKit, Vite, `@rollup/wasm-node` and esbuild's
  `@esbuild/linux-ia32` binary, all MIT-licensed, and their dependencies under
  their own licenses;
- for playgrounds with a `"server"`, the dev server's state in RAM and its
  caches on disk (`node_modules/.vite`, `.svelte-kit`);
- a snapshot of that system after boot and warm-up (`state.bin.zst`), which
  contains the guest's RAM: the kernel above and the agent from
  `guest/prebuilt/agent/`.

## External services used at runtime

These aren't files in the repository, but a deployment depends on them:

- **Microsoft's webview CDN** (`*.vscode-cdn.net`). Webviews such as the Markdown preview load from it when `WEBVIEW_HOST` in `web/boot.ts` is `null`, which is the case on any host other than `localhost`.
- **Open VSX** (`open-vsx.org`). Only used if `ENABLE_EXTENSION_GALLERY` in `web/boot.ts` is turned on. It is off by default.
- **Alpine's package mirror** (`dl-cdn.alpinelinux.org`). Reached only when a user runs `apk` inside the VM, through the network gate.

The dev container (`.devcontainer/`) uses `mcr.microsoft.com/devcontainers/javascript-node:1-22-bookworm`
and the `ghcr.io/devcontainers/features/go` and `docker-outside-of-docker` features.
These aren't part of the deployed site.
